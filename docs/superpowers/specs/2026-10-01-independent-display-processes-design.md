# 独立展示进程与现有功能等价迁移设计

状态：用户已明确暂缓独立进程拆分，当前通过不同窗口标题区分采集目标；本方案仅作未来参考，未经重新授权不进入迁移。彩带动画、弹窗图标配色和尺寸、应用图标与「玩播 · PlayCast」对外名称已被用户分别确认并在现有单应用结构中实现，内部存储标识保持不变。

## 1. 目标与验收原则

把现有同一 Electron 应用中的挑战展示、弹幕展示改成两个具有不同可执行文件名的独立展示程序。主工作台仍为唯一账号、采集、计数、存储与配置管理者。用户从原入口打开窗口，不增加额外登录或手动启动程序的步骤。

“1:1”指当前版本的可见行为、统计口径、操作顺序、隔离规则、保存语义和性能上限等价；不是重新实现一套近似功能。复用现有 React 展示组件与规则投影，迁移窗口托管和通信边界。新增的语义图标颜色是本次已讨论的视觉调整，不改变功能。

进程内存布局、跨进程延迟与总内存不可能承诺逐字节相同，需要实测。不能把独立 PID、不同 exe 名或 Electron 截图当成直播伴侣游戏采集已经通过。

## 2. 当前代码事实与不采用的过时要求

- `electron/main.cjs` 在一个主进程内创建主工作台、展示及配置窗口，通过 `webContents` 身份校验读写权限。
- `electron/display-windows.cjs` 管理单例、原生置顶、锁定穿透、显示尺寸、关闭协调及重建。
- `src/components/DisplayWindow.jsx`、`OverlayDisplay.jsx`、`MessageDisplay.jsx` 是需复用的展示层。
- 配置页使用 `DisplaySettingsWindow.jsx` / `src/live-settings.js`，修改即时应用并保存，不恢复旧的“预览后确认保存”流程。
- 弹幕展示只有深色；不因旧设计文档提到浅色而重新增加浅色。
- `electron/message-feed.cjs` 当前每类最多 200 条、每类保留记录最多 1 MiB，共五类最多 1000 条；去重键和连击键各有 20000 条上限。不能退回旧的共用 500 条窗口，也不能取消现有限制。
- 当前标题固定、防页面标题覆盖、步骤条留白、玩法滚轮与主工作台布局修复均保留。
- 旧文档与当前实现冲突时，以当前代码及本次用户明确要求为准；发现现有缺陷须单独记录，不静默改变计数或交互语义。

## 3. 程序与窗口归属

| 程序 | 窗口与职责 | 不承担的职责 |
| --- | --- | --- |
| `LiveInteractionTool.exe` | 工作台、登录窗口、挑战设置窗口、弹幕设置窗口；采集、计数、存档、快捷键、礼物目录 | 不再托管正式展示窗口 |
| `ChallengeDisplay.exe` | 仅挑战展示窗口，标题为「挑战展示 · Live Interaction Tool」 | 不登录、不采集、不算挑战、不读写挑战存档 |
| `DanmakuDisplay.exe` | 仅弹幕展示窗口，标题为「弹幕展示 · Live Interaction Tool」 | 不建立第二条抖音连接，不保存弹幕历史 |

- 每个展示端只有一个可采集的可见顶层窗口。点击其设置按钮仍打开独立配置页，但配置页由工作台程序持有，避免游戏采集误切到同进程的配置页。
- 每类展示最多一个实例。重复点击原来的“打开展示窗口”唤回实例，不新增一套程序。
- 展示端使用不同应用标识、程序文件名和窗口名称；验证任务栏分组与 Windows 文件描述，而不是只调用 `setTitle`。
- 仍是一套分发包，展示端由工作台按需启动。关掉一个展示只结束它及对应配置页，不停止采集、不结算挑战、不关闭另一展示。
- Electron 内部仍可能存在 GPU、渲染等辅助进程，不承诺任务管理器总共只显示三条进程。
- 不把两个展示都放入同一个 `DisplayHost.exe`，否则仍存在按程序名匹配时选错展示的可能。

## 4. 数据与通信

### 4.1 唯一状态来源

主程序继续拥有 `product.cjs`、平台适配器、游戏采集、挑战引擎、规则、挑战历史、礼物目录和所有持久化数据。展示端仅拿到自身当前已有的最小投影。

- 挑战端：现有 `createOverlaySnapshot` 投影与窗口状态。
- 弹幕端：现有房间连接状态、即时在线、能力、展示偏好、feed 版本及 `projectDisplayFeed` 增量投影。
- 账号 Cookie、完整用户资料、原始协议包、完整游戏快照、其他房间数据、历史详情均不得发往展示端。
- 主进程沿用现有采集和计数频率；不为每个展示重复建立游戏轮询、直播连接或统计器。
- 旧 `contextVersion`、feed `generation` / `after` 和保留 ID 语义保留；换账号、平台、房间或正式/演练来源，先失效并清屏，再接收新作用域数据。旧响应不能覆盖新内容。

### 4.2 本地专用通道

正式实现使用仅本机的 Windows 命名管道，不开放固定 TCP 端口，也不占用原 Vite 端口。

- 每个启动实例有独立连接身份和随机令牌，通过子进程专用启动通道交付，不写入账号配置、日志或公共文件。
- 服务端校验协议版本、启动实例、窗口种类、请求 ID、作用域版本和命令字段；不能仅信任请求携带的 `kind`。
- 展示端白名单只包含自身投影/增量读取、锁定/关闭/设置入口、必要的关闭协调及窗口状态。不能透传通用 `product.action` / 任意查询 / 任意文件操作。
- 消息分帧、单帧长度、缓冲区、在途请求与重试次数必须有界；异常或截断帧拒绝处理并断开，不能无限积攒未完成帧。
- 状态类更新只保留最新待发版本；弹幕维持至多一个增量请求在途，通过游标补齐当前保留范围，不建第二份无上限事件队列。
- 设置命令按现有顺序合并，不能因超时盲目重放带副作用的操作。重连后重新获取权威快照，不重放旧庆祝或跨账号输入。
- 切换作用域时优先失效旧快照；阻塞或断开的通道不能继续显示旧账号内容。失效无法确认时关闭相应展示并提示重开，不继续发送新范围数据。

## 6. 图标配色

在线浅金、评论薄荷绿、点赞柔粉、进场浅蓝、关注杏橙、礼物淡紫。两个展示端的同类图标共用语义颜色变量，在深灰和透明背景下保持辨识度。

- 给弹幕筛选入口、消息类型符号、挑战互动规则符号上色。
- 筛选选中态保留已有按下语义、底色与标识，不只靠颜色。
- 数值、正文保持清晰的中性前景色；锁定/设置/关闭仍使用中性控制色。
- 真实礼物图片保留原色，加载失败的礼物符号用礼物语义色。
- 不修改地区配图、整体布局或透明度语义。庆祝效果按用户随后确认的两侧彩纸/短彩带方案更新，不改变达成判定、播放次数及计数逻辑。

### 6.1 应用程序图标（用户补充，设计由实现方负责）

为三个程序制作一套原创、统一但可区分的图标，不使用默认 Electron 图标，不照搬英雄联盟或抖音标志。保持活泼、简洁和小尺寸辨识度，不添加难以阅读的小字或复杂背景。

- 主程序：珊瑚橙红，直播播放与互动信号图形。
- 挑战展示：暖金色，奖杯图形。
- 弹幕展示：青绿色，对话气泡图形。
- 三者统一外轮廓、视觉重量与留白；不只依赖颜色区分用途。
- 先用 Agnes 输出概念稿；概念稿不是直接用于安装包的最终图标，不把设计展示底板带入实际图标。
- 正式资源在项目内保存透明背景 PNG 和 Windows 多分辨率 ICO，至少覆盖 16、20、24、32、48、64、128、256 像素。16–32 像素单独检查并按需简化细节，避免直接缩小后糊成一团。
- 接入每个 EXE 的图标资源、对应原生窗口及桌面/开始菜单快捷方式；配置窗口沿用其所属功能图标。应用标识与任务栏分组一起验证，不能把网页 favicon 当成 EXE 图标已实现。
- 所有资源随分发包提供，离线可用；验证资源管理器、任务栏、Alt+Tab 的图标与窗口角色对应。图标缓存导致的旧显示需区分于资源缺失，不清理用户系统级缓存来掩盖问题。
- 不为图标修改已有业务规则、主题配图或用户数据。

## 7. 生命周期、故障与关闭

- 子程序只在打开对应展示时启动；不预启动两套空白 Electron。关闭后释放进程、订阅、指针检测和缓存。
- 展示端不持有账号持久化目录；界面会话使用内存隔离分区，必要运行文件使用应用自己限定的临时目录，并执行可恢复清理，不删除任何共享 Electron 安装文件。
- 设置页仍由主程序控制，配置实时发往原状态管线，再同步展示端；两种设置互不覆盖。
- 正常退出沿用保存与关闭协调。若任何有效配置保存失败，保留窗口并提示重试，不绕过守卫结束程序。
- 退出登录及作用域变化沿用现有行为：展示内容立即清空，旧配置销毁，已打开的展示可以保留等待状态；不擅自改变为继续显示旧内容。
- 恢复初始状态：先失效并停止所有展示通道、关闭配置与展示端，再完成既有会话/存档清理；不存在晚到消息重新写回旧状态的问题。失败与重试继续使用现有安全流程。
- 单个展示崩溃不影响主程序、采集或另一个展示。主程序记录该窗口已关闭，用户可从原入口重开；不无限自动重启。
- 主程序连接丢失时，展示端立即停止显示旧内容并退出，不长期悬留旧计数。恢复由工作台重新启动，窗口默认解锁。
- 管道 EOF、错误、失效请求和退出中的进程都有有界收尾。不能依赖只看 PID 是否存在的无限轮询。

## 8. 打包与存储连续性

现有项目尚未建立正式安装包工具链。本次必须把可执行文件名、Windows 文件描述、资源路径和主进程/展示端入口一并纳入构建验证，不能仅在代码中构造不同显示名称。

- 第一阶段使用隔离的可运行验证目录，独立 exe 名与独立进程必须真实存在，不修改 `node_modules/electron` 中原始程序。
- 正式阶段产出一套包含主程序和两个展示程序的可分发目录；共享静态资源/运行库是否可安全复用由打包验证决定，不复制三份用户缓存或存档。
- React 静态页面、主题图、徽章、图标及已有随包资源必须在离线 `file` 路径下可用，不能依赖 Vite 或本机素材目录。平台礼物远程图标沿用当前加载/失败占位行为，不承诺离线一定可见。
- 正式主程序继续使用既有应用数据位置、凭据保护和格式，不因 exe 改名悄悄迁移到新用户目录或显示“全新用户”。主程序单实例锁与展示端实例管理不能相互拦截。
- 不增加开机启动、常驻服务、管理员权限要求或外部网络服务。签名/发布不在未经授权的情况下执行。

## 9. 分阶段验收与停止条件

### A：独立进程采集可行性验证

用隔离配置与固定示例数据，产出两个不同文件名的展示程序，验证原生窗口标题、不同 PID/映像名称、同时运行、关闭互不影响以及资源加载。

用户在抖音直播伴侣「游戏采集」中分别选择它们，检查：

1. 同时存在两个可区分的目标，不选到工作台或配置页。
2. 显示正确画面，两个采集源不会串窗；关闭、重新打开后匹配是否稳定。
3. 透明度 0%、25%、100%，真实游戏背景前的透明效果/黑底行为。
4. 调整窗口尺寸、置顶、锁定/解锁后采集是否持续正常。
5. 主窗口最小化、切换前后台后画面持续刷新。

这是明确标注的测试样机，不是功能缩水的正式替代品，不操作真实用户账号/存档。若出现黑屏、无法枚举或无法保留透明效果，记录结果并与用户决定采集路线，不以“exe 不同名”宣告成功，也不直接替换现有实现。

### B：完整等价迁移

阶段 A 采集实测通过后，复用现有前端组件与投影，接入受限本机通信、即时配置、生命周期和打包入口。逐项对照第 5 节验收，并落实第 6 节配色与三个程序的本地图标资源。

### C：最终回归

- 运行现有全部单元测试、构建、窗口/配置/滚动/动画/账户/存储回归，以及新增跨进程身份、失效、重连、关闭、重建和坏消息测试。
- 采用隔离假账号、消息和临时目录，不触碰真实凭据或再次重置用户数据。
- 覆盖正常与最小窗口、四套主题、五种玩法、多个礼物/多页规则、长文字与大数值。
- 弹幕突发 5000 条以上，验证每类/总数/字节上限、DOM 虚拟化、在途请求和队列有界，隐藏后暂停、恢复后无旧作用域残留。
- 比较“仅主程序”“单展示”“双展示”“反复开关 20 次”下的进程树、内存、CPU、临时文件/缓存；不能仅观察单个 renderer 的内存而忽略独立 Electron 总开销。
- 100%/125%/150% 缩放、真实鼠标穿透、置顶游戏和直播伴侣采集需实机记录；未执行项明确标记未验证。
